Building a recipe, and choosing one to start from

The designer does two jobs. On the left you choose — and the hard part is that good flows get forked, so three different recipes can share one name. In the middle you build — and the screen refuses to save a recipe that can't actually run. This guide covers both, and every mark and control in between.

The library, and the same-name problem

Flows get forked. Someone takes the org's code-review, strips a step for speed, and publishes it under the same name — because it is code review. So a name alone can't tell you which recipe you're about to run, and picking the wrong one is how a security sweep silently stops happening.

One entry per name, expanded to compare

When two or more authors publish the same name, the rail collapses them into one entry with a count. Expanding it puts the variants side by side with the facts that actually separate them — never a name on its own.

Same name, 3 different recipes. Compare before you pick one.

What to compare, in what order

The shape glyph

Every entry carries a small diagram of its graph, so you can see whether a recipe branches or loops before you open it. Grey squares are steps; a dashed red arc is a route that sends work back.

Filtering is by domain, not by folder. The chips come from FlowBoard's role starter packs — Analysis, PO/PM, SDLC, QA, Platform, Design, Marketing — so a flow is filed by the job it does, not by who wrote it. Search matches names, authors and descriptions together, which is how you find "everything @team-sec published" in one go.

Reading the canvas

Steps are boxes, routes are edges. Everything you need to judge a recipe — what each step costs, which ones stop for you, and where work can loop — is on the graph itself.

Step states

Routes between steps

A route can always fire, or only when the step before it passed, or only when it failed. The last one is what makes a rework loop possible.

Branching and joining

Two things the graph says that a list of steps can't:

  • A fan-out — one step feeding several — means those steps run at the same time, each taking its own worker. It buys wall-clock time at the cost of parallel spend.
  • A join — several steps feeding one — means that step waits for all of them. review sits behind build and tests, so it cannot start on a half-finished task however fast one branch is.
The canvas is arrangement, not meaning. Dragging a step changes where it sits, never what runs when — that's the edges. Position is for your reading comfort, and it's saved with the version so the recipe looks the same to whoever opens it next.

Every setting on a step

Select a step to open it. Each field is a guardrail — the things that decide what a step may spend, how hard it thinks, and how much rope it has when running unattended.

Needs and produces — the contract between steps

Every step declares the files it must be given and the files it writes. Those declarations are what let steps hand off without a shared conversation: plan writes plan.md, and build reads it. They're also what the validator checks.

A requirement shows plain when some earlier step writes that file, and amber when nothing does. Outputs are always petrol — they're the promise this step makes to whatever comes next.

The one combination the inspector argues with: a step with no approval gate and no sandbox is an agent running unattended with full access to your machine. The inspector flags it rather than blocking it — but in the real product that's the combination the sandbox rule refuses outright.

Editing, validating, saving

You never edit a recipe in place. Editing produces a new version, and tasks already running keep the one they started on — which is why the status bar tells you how many are still on v4 while you're building v5.

What the validator checks

The two states of the strip

This recipe holds together — every step's inputs are written by a step before it.
won't save — 1 problem a step asks for a file nothing upstream writes

Each problem is a button — clicking it selects the offending step so you can fix it without hunting the canvas.

Draft mode isn't a version. It forces every step onto the cheapest model while you're iterating on the recipe rather than the code, and the cost ceiling in the canvas bar drops to match. It's a switch on how runs execute, not an edit to the flow, so it never makes a new version and never shows as unsaved.
