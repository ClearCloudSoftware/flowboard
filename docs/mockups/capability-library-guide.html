The building blocks steps draw on

Flows reference capabilities; the library is where those come from. The one idea to get right before anything else: a capability is the logical thing a step asks for, and a pack is one packaging of it for one agent CLI. Almost everything odd about this screen follows from that.

A capability is not a pack

A step says "run code-review". It does not say how. The capability is that logical name. A pack is the actual bundle of files one agent CLI knows how to mount — for Claude Code that's a plugin directory; another provider has its own format. The registry stores the packs; the adapter knows how to mount them.

The three kinds

A pack is a bundle, not a wrapper. Installing one installs every skill, agent and flow inside it. Removing it leaves behind anything a flow still draws on — the library will not pull the rug out from under a running recipe.

Marks in the rail

One dot per row, carrying the only three states worth interrupting you for.

Each row also carries its author, the providers it's packaged for, and its use count — so the rail answers "whose is this, will it work here, does anything need it" without opening it.

Tools, and why some are amber

Every capability declares the tools it may use. Most are local and unremarkable. The ones that can reach outside the workspace are marked, because they interact with the sandbox:

ReadGrep WriteEdit
Installing a capability does not open the wall. Egress is default-deny at the step, not the capability. A skill that asks for WebFetch will still fail closed until the host it needs is on that step's allowlist — which is exactly the failure that burned $0.48 on the build in the task detail screen.

So the amber chip is not a warning that something is unsafe. It is a note that this capability will not work until someone also changes a step's allowlist — and that you should know which host before you approve that change.

Updating and removing

Updating changes every flow at once

This is the asymmetry worth knowing. A task is pinned to the flow version it started on, so editing a flow never disturbs work in flight. A flow is not pinned to a capability version. Update secret-scan from 1.3 to 1.5 and every flow that draws on it uses 1.5 on its next run — immediately, with no version bump of its own.

So read the update note before you take it. "Stops flagging example keys in docs" sounds harmless until you notice it also means a real key in a docs file stops being caught. The library shows you the note; it cannot decide for you.

Removing is blocked while anything uses it

The used by list is the check. Anything referenced by a step cannot be removed, and the button says how many steps are holding it. A capability nothing uses shows a hollow dot in the rail and can go — the argument for removing it is that every installed capability is another row in the step editor's picker.

Removing is the only destructive action here, and it is the only one the screen refuses outright. Everything else — installing, updating, defining an agent — is additive or reversible by re-installing from the same commit.
